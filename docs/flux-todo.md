# Flux CD: список задач

Цель: после установки K3s Ansible запускает первоначальную настройку Flux, а дальнейшее состояние кластера задаётся манифестами в `infra-deploy`. Workflow приложений только собирают образы и публикуют их в registry; Flux отслеживает digest обновляемого тега каждой ветки и разворачивает новую версию.

## Первоначальная настройка

- [x] Закрепить версии Flux CLI и контроллеров в Ansible bootstrap.
- [ ] Подготовить в Git точку входа `clusters/homelab/` и отдельные каталоги для инфраструктуры и приложений. Добавлять ресурсы в синхронизацию явно, чтобы можно было задать порядок их применения.
- [ ] Определить доступ Flux к Git для автоматизации образов: ей нужна запись коммитов с новым digest. Запланированный ключ только для чтения для этого не подходит. Выбрать права на запись для deploy key или отдельные учётные данные для автоматизации.
- [x] Добавить Ansible playbook после K3s для `flux bootstrap github` существующего `De333mond/infra-deploy` с `--personal` и путём `clusters/homelab/`. Передавать GitHub PAT из `local/` без вывода в логи и без хранения PAT в Kubernetes. Первоначально устанавливать только `source-controller` и `kustomize-controller`.
- [x] Добавить `helm-controller` для HelmRelease Traefik. В кластере появится после применения изменений из Git.
- [ ] Добавить `image-reflector-controller` и `image-automation-controller`, когда появятся соответствующие ресурсы.
- [ ] Учесть, что bootstrap создаёт коммит в GitHub: синхронизировать локальный checkout после запуска и проверить повторный запуск playbook.
- [ ] Проверить доступность контроллеров Flux и синхронизацию репозитория на чистом K3s.

## Секреты

- [ ] Добавить в Ansible создание age-ключа в исключённом из Git `local/` только при его отсутствии; выставить права на файл и предусмотреть восстановление существующего ключа на новой машине. Не генерировать новый ключ при повторном запуске.
- [ ] Сохранить резервную копию закрытого age-ключа вне компьютера и кластера. Публичный ключ указать в конфигурации SOPS в Git.
- [ ] Передать закрытый ключ через API Kubernetes в Secret namespace `flux-system` до применения зашифрованных манифестов; не выводить его в логи Ansible.
- [ ] Настроить Flux Kustomization с `decryption.provider: sops` и ссылкой на Secret с age-ключом. Проверить расшифровку тестового Secret из Git.

## Ресурсы кластера

- [x] Подготовить Traefik как HelmRelease под управлением Flux с сервисом ClusterIP. Внешний доступ настроить после выбора маршрута.
- [ ] Описать установку registry через Flux с постоянным хранилищем, адресом, TLS и учётными данными для push/pull. Registry должен запускаться из доступного готового образа, без зависимости от образов приложений.
- [ ] Определить способ установки runner и описать его через Flux; для варианта ARC настроить доступ к репозиторию личного аккаунта и последующий переход к организации.
- [ ] Разделить инфраструктуру и приложения на Flux Kustomization и задать зависимости там, где приложению нужны готовые инфраструктурные компоненты.
- [ ] Для сервисов хранить обычные параметры в ConfigMap, а секреты — в зашифрованных SOPS-манифестах. Предусмотреть обновление pod при изменении переменных окружения.

## Обновление образов

- [ ] Определить имена обновляемых тегов по веткам и проверить доступ Flux к registry (включая авторизацию и TLS).
- [ ] Для каждого приложения настроить `ImageRepository` и `ImagePolicy`, которая отслеживает digest соответствующего тега с `digestReflectionPolicy: Always`.
- [ ] Настроить `ImageUpdateAutomation`: Flux записывает новый digest в манифест и коммитит изменение в `infra-deploy`; изменение Pod template запускает развёртывание. Workflow не меняет манифесты.
- [ ] Проверить полный цикл: первая публикация образа, повторная публикация под тем же тегом, коммит нового digest от Flux и обновление pod. Проверить восстановление Flux и секретов на чистой ноде.
