# Решения по развёртыванию

Обновлено: 2026-10-16. Этот файл фиксирует требования и выбранное направление. Пункты в разделе «Открытые вопросы» ещё не считаются решёнными.

## Принято

- `infra-deploy` — Git-репозиторий для конфигурации инфраструктуры и манифестов развёртывания. Изменения манифестов должны применяться после коммита через Flux CD.
- Новая машина должна разворачиваться с минимальным количеством ручных действий. Ansible уже отвечает за подготовку хоста и установку K3s.
- На основной ноде нужен собственный container registry с постоянным хранилищем.
- На этой же ноде должен автоматически появляться GitHub Actions runner. Сейчас репозиторий находится в личном аккаунте `De333mond`; возможность runner на уровне организации понадобится после появления организации.
- Секреты деплоя должны иметь отдельный механизм хранения и не попадать в Git открытым текстом.
- Локальный inventory остаётся в `ansible/inventory/hosts.yaml`. Исходные секреты для первоначальной настройки кладутся в исключённый из Git каталог `local/`.
- Пока сервер работает как виртуальная машина в домашней сети, входящий доступ идёт через публичный VPS и прокси-туннель до виртуальной машины. На этапе продакшена целевой сервер будет иметь собственный публичный IP.

## Потенциальное требование

В будущем инфраструктура может охватить несколько выданных под проекты серверов. Тогда для каждого сервиса потребуется указывать целевой сервер в Git. Серверы могут быть независимыми, без общего Kubernetes-кластера и без репликации сервисов между ними. Сейчас эту схему не реализуем; при выборе структуры манифестов, конфигурации Flux, registry и способа передачи секретов не следует жёстко привязывать их к одному серверу.

## Рабочая схема (пока не утверждена)

1. Ansible готовит текущий сервер и устанавливает K3s. Затем отдельный шаг Ansible запускает на сервере `flux bootstrap github` для существующего `De333mond/infra-deploy` с путём `clusters/homelab/`. Команда устанавливает контроллеры Flux, коммитит их манифесты в репозиторий и настраивает синхронизацию.
2. Flux читает манифесты из этого репозитория и применяет их на текущем сервере.
3. Workflow приложения собирает образ и отправляет его в registry под обновляемым тегом ветки. Flux отслеживает digest этого тега, записывает новый digest в `infra-deploy` через image automation и разворачивает образ.
4. Registry и runner создаются автоматически после первоначальной настройки.
5. Секреты приложений и кластера шифруются через SOPS с age. В GitHub хранятся зашифрованные манифесты; Flux скачивает их и расшифровывает в K3s. Закрытый ключ age передаётся серверу при первоначальной настройке и хранится в резервной копии вне GitHub. Если появятся независимые серверы, для них можно использовать отдельные ключи.
6. Публичные адреса сервисов задаются отдельно от адресов VPS и виртуальной машины, чтобы позже переключить входящий маршрут на публичный IP целевого сервера.

GitHub Actions Secrets используются для учётных данных, которые нужны workflow, например для отправки образов в registry. Они не служат источником секретов для Flux. Учётные данные, необходимые для первоначальной настройки Flux и ключ age, не записываются в репозиторий открытым текстом.

При bootstrap Flux GitHub PAT читается из `local/github-token` и передаётся Ansible без записи в логи. Flux подключается к Git по SSH deploy key; `--token-auth` не используется, чтобы PAT не сохранялся в Kubernetes Secret. Сначала ставятся только `source-controller` и `kustomize-controller`; дополнительные контроллеры появятся вместе с ресурсами, которым они нужны. Для image automation нужен доступ на запись в Git; способ выдачи этого доступа ещё предстоит выбрать. После bootstrap локальный checkout нужно синхронизировать с коммитами, которые команда отправила в GitHub. Версии Flux CLI и контроллеров закреплены в конфигурации развёртывания.

## Открытые вопросы

- Адрес текущего registry, доступ CI и TLS-сертификат.
- Какие сервисы должны быть доступны через VPS, как устроены прокси-туннель и завершение TLS.
- Какие репозитории должны использовать runner, пока инфраструктура находится в личном GitHub-аккаунте.
- Механизм runner: контроллер ARC в K3s или системный сервис на хосте.
- Как получать bootstrap PAT и где хранить резервную копию ключа age при развёртывании чистой машины.
- Срок действия bootstrap PAT и порядок обновления связанного с ним GitHub deploy key.
- Права записи в Git для Flux image automation: deploy key с правом записи или отдельные учётные данные.
